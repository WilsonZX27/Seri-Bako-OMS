# Isolated session recovery candidate — not released

Base: last confirmed production168,87939e569be3d73f238962227bada67b751cef42.169b33fc1ca50e54267010eaf66f95f0c7b224855c0 and170b0ed9671c4451ec1fefdcd41f54ca0a1e3741e98 have identical affected auth files; those releases do not include this candidate. No release metadata/SQL/role/tenant/idle duration change. Only integration may merge/release after current-base verification.

Cause: middleware classifies explicit Auth400 invalid refresh/session/JWT errors as temporary outages and returns JSON even for document navigation. Its early Auth/API denial responses can drop SDK-issued cookie refresh/cleanup, leaving an old browser state unable to recover. Independently, the installed SSR SDK throws while decoding malformed base64 session cookies before ordinary login initialization.

Correction: recognize only definitive SDK credential codes/names as expired; preserve unknown400/403/429/network errors as unavailable. Keep SDK error codes on rejected promises. All replacement middleware responses forward only SDK-issued cookie updates. Expired API/write requests get401 without redirect/replay. Document503 responses have a noncacheable static recovery page, manual retry and safe login link. Existing safe return-path helper preserves the bookmark path without query secrets. All existing user/staff/role/tenant permission checks remain.

The shared server/middleware cookie reader uses the installed SDK's own chunk/decoder utilities. Only a currently configured project session whose base64 encoding cannot be decoded is ignored in-memory; names remain visible for a later explicit SDK sign-in to replace old chunks. Valid sessions, raw JSON inputs, other-project cookies, PKCE verifier and preferences are unchanged. It never writes/deletes browser cookies itself, fabricates a token or trusts an unverified user. Public login stays reachable. Do not classify arbitrary syntax/network errors as expired or force global signout.

Consumers: middleware, server profile query and workspace error boundary share classification; both server cookie adapters share the reader. The recovery helper is middleware-only. Existing idle/multitab policy, auth actions, browser Supabase client, permissions and business mutations are unchanged. The tablet scrolling issue belongs to a separate task.

Verification includes failing-before/pass-after navigation tests, existing offboarding/permission/return-path regressions, real SDK synthetic expired/revoked/valid/malformed cookie and explicit sign-in tests, and a disposable Chromium cookie-navigation fixture with actual middleware/SDK. Fixture Auth/user/profile/permission transport and login page are synthetic; no real accounts, cookies or external requests are involved. Chromium mobile emulation is not real iOS/WebKit acceptance. Source168 has a pre-existing documentation-authority failure caused by lowercase preview heading; retain it as baseline evidence rather than mixing unrelated release documentation into this patch. See exact handoff report for final counts/build/hash and170 combination results.

Required real-device acceptance after separately approved Preview/release: actual failing iPhone Chrome and home-screen entry, old bookmark/full URL, same-context new login, refresh and return after idle, temporary service failure, valid existing sessions, role/tenant denial and no automatic business submission replay. Do not require deleting all history/cache. If a real transient Auth outage remains, keep fail-closed and use request-time/code diagnostics without tokens/cookie values.
