## 结论先说

系统不是“彻底坏掉”，但已经从单纯功能开发进入“需要整理架构和上线边界”的阶段。当前适合继续盘点和局部重构，不适合继续无边界加功能，也不适合直接上线。

本盘点为只读盘点：没有删除文件、修改生产数据、执行线上迁移或部署。

## 已确认的结构性问题

1. 历史迁移不断叠加，当前已有 089 号迁移；不能通过随意删除旧迁移来“清理”。
2. 部分旧权限政策和旧入口曾与新规则并存，导致局部修复可能被旧路径绕过。
3. 后台管理逻辑过度集中在 `foundation.ts`，后续维护容易牵一发动全身。
4. 库存、生产、调拨、损耗的正确性依赖数据库原子事务，不能只靠页面按钮限制。
5. 静态合同测试很多，但它们不能完全替代双公司、并发、失败回滚和真实角色 E2E。

## 第一版上线建议范围

建议第一版只承诺：

- 登录和员工角色；
- 公司/分店基础资料；
- 物料、供应商和单位；
- 采购申请、采购单、收货；
- 库存余额和库存流水；
- 基础生产任务；
- 门店日记录；
- 基础报表和审计记录。

暂不承诺：高级成本、复杂预测、全部历史兼容入口、所有报表、非核心批量操作。

## 下一步处理方式

1. 冻结新功能和随意小修小补。
2. 已修复库存生产过账授权契约；当前合同测试 179/179 通过，typecheck、lint、build 通过。
3. 在干净测试数据库完整执行 081–089 迁移；当前 Supabase CLI 状态检查被本机 telemetry 文件权限阻塞，数据库验证仍未完成。
4. 为核心模块建立唯一写入入口和状态机。
5. 对重复/旧路由只做标记和重定向，暂不直接删除。
6. 完成双公司、角色、并发库存和失败回滚验证。
7. 只有在上述验证通过后，才决定某个模块是保留、局部重写还是整体替换。

## 需要业务方确认的事项

- 第一版是否只覆盖上述核心范围；
- 是否允许暂时关闭高级报表和历史兼容入口；
- 库存是否允许负数；
- 生产过账失败时必须完全回滚；
- 是否需要支持多公司，还是先只服务一个公司；
- 第一版正式上线的目标日期。
